AI 异步调用契约与流程

目标：主系统上传图片后自动触发 AI，医生可手动重跑，同时不阻塞页面。

核心原则

主系统与 AI 服务解耦

主系统不等待模型立即返回诊断结果，而是先创建任务并记录状态，再由后台异步处理并落库。这样上传流程稳定，AI 慢一点也不会拖垮前台体验。

推荐职责分工

业务系统管任务状态，FastAPI 管模型推理

Next.js 后端负责创建任务、重试、鉴权、结果落库；FastAPI 只暴露 AI 任务接口，专注于取图、推理、返回结构化结果。

异步时序

上传自动跑 + 医生手动重跑

1. 患者上传图片
主系统生成 image_id
→
2. 主系统建任务
ai_task.status = queued
→
3. Worker 调 FastAPI
POST /ai/tasks
→
4. FastAPI 推理
running → succeeded / failed
→
5. 主系统写回
AIResult.image_id + task 状态
主系统内部建议新增表：AITask
  • id
  • image_id
  • trigger_source: auto / manual
  • status: queued / running / succeeded / failed
  • retry_count
  • requested_by_user_id，可为空
  • provider_task_id，可为空
  • error_message
  • started_at / finished_at
FastAPI 服务最小接口
  • POST /ai/tasks 创建推理任务
  • GET /ai/tasks/{task_id} 查询任务状态
  • 可选：POST /ai/tasks/{task_id}/cancel
POST /ai/tasks { "image_id": "img_123", "image_url": "https://storage/...jpg", "callback_token": "internal-secret", "labels_version": "v1" }
FastAPI 任务状态返回
GET /ai/tasks/{task_id} { "task_id": "task_456", "status": "succeeded", "result": { "category": "周围皮肤并发症", "label": "刺激性皮炎", "confidence": 0.93, "raw_result": {} }, "error": null }
主系统侧推荐处理
  • 上传完成后立即返回前端，不等 AI 结束
  • 随访详情页显示 AI 状态：排队中 / 分析中 / 已完成 / 失败
  • 医生点击重跑时，新建一条 AITask，不覆盖历史任务
  • AIResult 存当前有效结果，AITask 保留完整执行历史
我对一期的推荐

先用“主系统轮询 FastAPI 任务状态”的方式最稳，不必一开始就做回调。也就是主系统创建任务后，由后台 worker 定时轮询 FastAPI，拿到结果再写回数据库。等以后需要更高吞吐或更低延迟，再升级成回调 webhook。
