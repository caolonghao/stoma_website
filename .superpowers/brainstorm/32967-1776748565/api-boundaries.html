设计段落 3：后端 API 边界与 AI 接口预留

目标是让医生端和患者端共享一套后端，但权限边界清楚，后续接 AI 时也不用推翻接口。

接口组织方式

统一后端，按资源分组，按角色控权

我更推荐 API 不强行按 /doctor/* 和 /patient/* 完全拆开，而是统一用资源型路径，再在服务端做角色校验。这样能减少重复接口，也更利于维护。

鉴权建议

会话或 JWT 都可，但首期更推荐服务端会话

如果一期主要是网页系统，推荐用基于 Cookie 的会话登录，前端更省心；如果你们后面准备加小程序或 App，再切 JWT 也不晚。

1. Auth 认证接口
  • 患者注册
  • 医生/患者登录
  • 获取当前用户信息
  • 退出登录
/api/auth/*
2. Patients 患者档案接口
  • 医生端：患者检索、创建、详情、编辑
  • 患者端：查看自己的基础资料
/api/patients/*
3. FollowUps 随访接口
  • 按患者查询随访列表
  • 查看单次随访详情
  • 按拍摄日期自动归档或补建随访
/api/followups/*
4. Images 影像接口
  • 上传图片并填写拍摄日期、体位
  • 获取某次随访下的图片列表
  • 删除或替换异常图片
/api/images/*
5. AI 结果接口
  • 对单张图片发起 AI 辅助诊断
  • 查询该图片的 AI 结果
  • 后续可异步轮询状态
/api/ai/*
6. Reports 人工报告接口
  • 医生保存随访综合报告
  • 患者查看自己的最终报告
  • 支持草稿和最终提交
/api/reports/*
AI 预留方式

推荐做成异步任务，而不是把 AI 逻辑写死在上传接口里

图片上传
生成 image_id
→
调用 AI 按钮
POST /api/ai/tasks
→
任务执行
后端调用外部 AI 服务
→
结果落库
AIResult.image_id
医生端权限边界

医生可调用

全部患者查询、全部随访查看、手工建档、影像上传、AI 触发、人工报告填写。

患者端权限边界

患者可调用

注册登录、查看自己的档案与随访、上传自己的影像、查看自己的最终报告，但不能改 AI 结果和医生报告。
